# BJM 通用迁移包 v1.12.1

在本仓库 v1.10.1 上合入作者交来的 v1.12 包里 v1.11、v1.12 两版新加的东西，再按复核改了几处。v1.11 是作者在自己的 v1.10 上做的，v1.12 又在 v1.11 上做，两版都没有单独发布到本仓库；在本仓库里，这一版接在 v1.10.1 后面。协议的规则、`SKILL.md`、`scripts/`、`tests/`、检查点格式和图执行器的数据库结构与 v1.10.1 相同，v1.10.1 的检查点和图执行器数据库照旧能用；协议只改了附录 C“改编依据”里的一句说明。

## 下载哪一个

- **`bjm-portable-v1.12.1.zip`**：整个包，解压出来是 `bjm-portable/` 目录，和仓库里这一版的文件相同（`.github/`、`docs/releases/` 这类仓库用的文件不进包）。由发布工作流从这一版的提交用 `git archive` 生成。
- `LICENSE`、`THIRD-PARTY-NOTICES.md`：许可全文和第三方组件说明，包里也有同样的两份。

## 这一版改了什么

- **分页读取执行记录（来自 v1.11）**：图执行器的 `events` 新加可选的 `--after ID` 和 `--limit N`。`--after` 填上次读到的最后一条事件的 `id`（第一次用 0），只返回这个运行里 ID 比它大的事件；`--limit` 一次最多返回 N 条，只能和 `--after` 一起用。不加这两个选项时，输出和 v1.10.1 逐字节相同。用法见 `graph-runtime/README.md` 的“分页读取执行记录”。
- **只由 `init` 建库（来自 v1.12）**：`init` 以外的命令遇到没初始化的文件（空文件，或者别的程序建的 SQLite 库），报 `database is not initialized; run init first`，退出码 2，文件不变，也不留锁文件。v1.10.1 遇到空文件会先写进表结构、留下锁文件，再报错。路径不存在时照旧报 `database does not exist`。在 Python 里直接用 `Engine(路径)` 仍会建表，`Engine(路径, initialize=False)` 才和命令行一样。
- **打开库以前检查线程上限（来自 v1.12）**：`run --workers` 或 `--claude-workers` 不是正整数时，在打开库以前就报错退出，退出码 2。
- **Agent Skills 0.6.18（来自 v1.11）**：`vendor/` 从 0.6.17 换成 0.6.18。模块仍是 26 个；用到共享清单的 12 个模块在自己的 `references/shared/` 下另带一份副本，只取一个模块时也能打开。`README.md`、`references/methods.md`、`THIRD-PARTY-NOTICES.md` 和协议附录 C 跟着改。
- **按复核改的地方**：
  - 线程上限的报错：v1.12 用 argparse 的 `parser.error` 报，先打出总命令的用法；现在和图执行器的其他报错一样，只打一行 `workflow: --workers must be a positive integer` 或 `workflow: --claude-workers must be a positive integer`，后者和 v1.10.1 一字不差。`run_tasks` 里那道从命令行已经走不到的检查删掉。
  - 保留 v1.10.1 在引擎里要求 `worker_limits` 是映射的检查，v1.12 包里没有这一处。
  - 图执行器改称 v0.1.9。v0.1.7 这个号作者那条线和本仓库各用了一次，指的不是同一样东西；v1.12 包里的 v0.1.8 没有本仓库的修正。这一版是两边合起来再改了报错，不沿用 v0.1.8。
  - 测试：v1.11 的两项和 v1.12 的一项移过来；只由 `init` 建库那项加上 `retry`、`edit`、`approve`、`reject`、`resolve`，并核对报错的写法。v1.12 在 Claude Code 命令行测试里的改法和 v1.10.1 的等价，取 v1.10.1 的。
  - 说明文字：`graph-runtime/README.md` 的初始化一段写明 `init` 以外的命令都这样；分页一节挪到“运行回归测试”前面（v1.12 把它插在演示步骤中间，后面一节开头的“上一步”就指错了），并写明 `--limit` 只能和 `--after` 一起用；v1.12 在设计参考里加的 Temporal Python SDK 1.37.0 和“公开版 v1.10.1”两条没有取。`README.md` 的下载按钮、测试说明和令牌一句保留仓库的写法，只改版本和数目，另加一句分页的用法。`THIRD-PARTY-NOTICES.md` 新加一条，写明 v1.11、v1.12 两节链接的项目只作参考。`CHANGELOG.md` 收录了 v1.12 包自带的 v1.12、v1.11 两节，并在和本仓库版本线对不上的地方加了注，其中 Temporal 那一条的“参考”说过了头，加注写明了 1.37.0 实际改的是什么。
  - 本仓库 v1.10.1 的版本记录和说明里“取值不对时库里什么也不写”的说法，只对已经 `init` 过的库成立；这一版起对空文件也成立。

## 验证到哪一步

- `tests/` 下 53 项（BJM 36 项、匿名对照材料 12 项、收票 5 项）：在 Linux 上用 Python 3.11.17、3.12.3、3.13.17 各跑一遍，全部通过。
- `graph-runtime/tests/` 下 41 项（v1.9.1 的 33 项、v1.10 的 2 项、v1.10.1 的 3 项、v1.11 的 2 项、v1.12 的 1 项）：在 Linux 上用 Python 3.11、3.12、3.13 各连跑 5 遍，共 15 遍，每遍 41 项全部通过，没有跳过的项。跑测试时命令搜索路径只有 `/usr/bin` 和 `/bin`，在那里找不到真的 `claude`；`test_claude_cli.py` 照旧只把模拟程序所在的目录交给子进程。复核时在只做了三方合并的副本上，三个版本各连跑 10 遍，共 30 遍，也都通过。
- 错误改法：在这一版的代码副本里逐一造了 10 种错误改法，各跑一遍图执行器的测试，每一种都有测试失败：游标改成 `>=`、命令行总是建库、去掉 `--workers` 预检、分页不按运行过滤、`limit` 不要求 `after`、去掉上限、去掉 `main` 里的 `--claude-workers` 预检、忽略 `limit`、线程上限改回 `parser.error` 报错、去掉 `worker_limits` 必须是映射的检查。
- 空文件对照：对一个空文件，分别用 v1.10.1 和这一版跑 `status`、`events`、`events --after -1`、`events --after 0 --limit 0`、`run`、`run --workers 0`、`run --claude-workers 0`、`retry`、`approve`、`reject`、`edit`、`resolve`。v1.10.1 除了不认的两条 `events` 选项，都先把文件写成 24,576 字节、留下 `.lock`，再以退出码 2 退出；这一版都以退出码 2 退出，文件仍是 0 字节，目录里没有锁文件。作者的 v1.10 和 v1.10.1 一样。别的程序建的 SQLite 库，这一版的 `status`、`events`、`run` 都报没初始化，文件的 SHA-256 不变。之后 `init` 能初始化同一个路径。
- 分页：同一个库里有两个运行时，按每页 2 条读到的拼起来等于完整记录，只含这个运行的事件；游标在末尾之后返回 `[]`；`retry` 和 `run` 追加事件以后，从原来的末尾续读，读到的正好是新加的那些。一边跑 40 个节点、3 个线程的图，一边按每页 3 条轮询，跑了 10 轮，每轮 81 条事件、运行期间轮询 31 到 34 次，拼出来的记录每轮都和完整记录相同，没有重复，也没有缺漏。
- 演示 `graph-runtime/demo.py`：在 Python 3.11、3.12、3.13 上各跑一遍，再在 3.13 上连续跑 30 次，都通过。复核时还在 3.12 上照 `graph-runtime/README.md` 的 Bash 逐步命令做了一遍（失败、重试、续跑、`events --after 0 --limit 100`、改稿、旧令牌被拒、新令牌批准），和说明一致。
- 兼容：用两章演示图，同一个库在 v1.10.1 和这一版之间交替运行，两个方向各一遍：一版跑出失败，另一版 `retry` 后只补跑失败的一支，另一支沿用原结果；再跑一遍状态不变；一版发的令牌由另一版退回，被退回的令牌不能再批准；改稿后发新令牌，旧令牌被拒，新令牌由另一版批准；这一版分页读到的拼起来等于完整记录；两版不带参数的 `events` 输出逐字节相同；`user_version` 仍是 1，两个方向建出的库结构文字相同。在 Python 3.11、3.12、3.13 上都是 29 项核对全过。同样的核对在作者的 v1.10 和这一版、本仓库 v1.9.1 和这一版之间也全过。v1.4 和 v1.8.1 建库并跑出失败的库，这一版能重试、续跑、分页，旧版能批准这一版发的令牌。v1.10.1 遇到 `events --after` 报用法错误，退出码 2。
- Agent Skills 0.6.18：作者包里的 ZIP 是 649,475 字节，SHA-256 `d6bade14…4065`，注释记的提交是 `e997ac5b…`。GitHub 的官方源码 ZIP 取不到，用 git 取下 0.6.18 标签，在 `TZ=America/Los_Angeles` 下 `git archive` 打出的 ZIP 和它逐字节相同；同样的办法打 0.6.17，得到的就是仓库里那份已经和官方 ZIP 比过的 ZIP。展开目录从这份 ZIP 解出：279 个普通文件和 ZIP 逐字节相同，符号链接 `.opencode/skills` 只留在 ZIP 里，9 个 shell 脚本照 ZIP 保留可执行位。和 0.6.17 比，文件新增 18 个、改了 39 个、删除 0 个，`LICENSE` 逐字节相同。`references/methods.md` 的 26 个模块链接都能打开；附录 C 表里的 12 个上游路径都还在，其中 5 个在 0.6.18 里改过。`vendor/` 下的脚本一律没有运行。
- v1.12 的包和基线：作者交来的 v1.12 包是 1,327,979 字节，SHA-256 `160be250…5241`，309 个文件；作者先前交来的 v1.10 包算出的 SHA-256 和 v1.11 一节记的 `c1363aa6…c647` 相同。三方合并以 v1.10 包为底；v1.12 包里改过的文件先全部读过，再放进仓库的副本里运行，交来的目录本身只读，没有在里面运行任何东西。
- 用发布工作流同一条 `git archive` 命令在临时克隆里模拟了发布包：包里 309 个文件，路径和作者的 v1.12 包相同，内容不同的是 11 个（`CHANGELOG.md`、`README.md`、`THIRD-PARTY-NOTICES.md`、`graph-runtime/` 下的 `README.md`、`engine.py`、`workflow.py` 和三个测试文件、`references/` 下的两份），`vendor/` 和 v1.12 包逐字节相同；包里的文件和仓库里这一版的文件逐个相同；包的根目录没有 `.github/`、`docs/releases/`、`.gitattributes` 和 `.gitignore`（`vendor/` 里上游自带的同名文件照原样保留），`vendor/` 下 9 个 shell 脚本保留了可执行位；解开后在 Python 3.12 上两套测试和演示都通过。
- 外部引用：v1.11、v1.12 两节引的 Agent Skills 0.6.18、达尔文 v3.0.2、Temporal Python SDK 1.37.0、Google ADK v2.15.1、OpenAI Agents SDK v0.26.0、LangGraph 1.2.24 和 LangGraph CLI 0.4.44，用 git 核了标签、提交和日期，都对得上；Temporal 1.37.0 还读了上游版本记录里这一版的改动。arXiv 上那篇论文的摘要页取到了，题目和日期核过。本仓库 v1.10.1 的发布页核过。
- 泄露检查：改动的文件里没有私人路径，也没有新加的个人信息。
- 测试和检查都是同一个模型（Claude）的新实例做的，不是独立评审。

## 没有验证的

- v1.11 包没有交来：它的 SHA-256、它记的“132 条、30,292 字节”这组对照数字，以及 v1.11 和 v1.10、v1.12 之间的双向续跑都没有核对，只拿作者的 v1.10 和 v1.12 代替做了。
- 作者写的“从最终 ZIP 解压后通过”：这次测的是解出来的文件，没有从作者的 ZIP 重新打包再跑。
- 真实的 Claude Code 调用，和以前几版一样没有用真的 `claude` 试过。
- 按 Ctrl-C 中断时分页会怎样，没有试；有人手工删掉末尾几条事件、ID 被重新用到的情况不属于正常用法，没有测。
- Agent Skills 0.6.18 的官方源码 ZIP 和发布页取不到，“正式版”和发布时刻没有核到；13 份 `SKILL.md` 的改动只看了大意，没有逐条审读，新模块资料和 BJM 一起用的效果没有测。v1.11、v1.12 引的其他项目的发布页也都打不开。
